# jyotish-map

Система разбора карты Джйотиш: методика из десяти промптов плюс код, который
берёт на себя то, что не должна делать языковая модель.

Подключается двумя способами: как **плагин Claude Code** из маркетплейса в этом
же репозитории и как **скилл в открытом формате Agent Skills** — его читают
ChatGPT, Codex и другие агенты.

```
.claude-plugin/marketplace.json    манифест маркетплейса Claude Code
.agents/skills/jyotish-reading     путь обнаружения по открытому стандарту
plugins/jyotish/
├── skills/jyotish-reading/        самодостаточный бандл Agent Skills
│   ├── SKILL.md                   как вести разбор: порядок, гейты, правила
│   ├── references/                методика: 00_README и промпты 01…10
│   ├── assets/                    шаблон вёрстки клиентского PDF
│   └── scripts/jyotish            запуск CLI, если он доступен
├── commands/                      команды /jyotish:* (только Claude Code)
├── jyotish/                       код: сбор, расчёты, проверки
└── tests/
scripts/build-skill.sh             собрать zip для загрузки в ChatGPT
ARCHITECTURE.md                    что автоматизируется, что остаётся человеку
```

Методика в `references/` — единственный источник правды о том, как ведётся
разбор. Код не заменяет её, а исполняет ту часть, которую нельзя доверять
языковой модели.

Скилл лежит в **[открытом формате Agent Skills](https://developers.openai.com/api/docs/guides/tools-skills)**,
который читают и Claude, и ChatGPT, и Codex. Копия одна: каталог
`plugins/jyotish/skills/jyotish-reading/` и есть бандл, `.agents/skills/` —
ссылка на него.

## Установка

### Claude Code

```
/plugin marketplace add serg123e/jyotish-map
/plugin install jyotish@jyotish-map
```

Появятся команды `/jyotish:new`, `/jyotish:collect`, `/jyotish:stage`,
`/jyotish:soul-path`, `/jyotish:check`, `/jyotish:status` и скилл, который
ведёт разбор по этапам и не даёт проскочить гейты.

Больше ничего ставить не нужно: каталог `bin/` плагина Claude Code сам добавляет
в PATH, а `jyotish` — это launcher, который при первом вызове поднимает
изолированный venv в каталоге данных плагина. Первый запуск ~15 секунд, дальше
мгновенно, системный Python не трогается.

### ChatGPT, Codex и другие агенты по открытому стандарту

Соберите бандл и загрузите его как скилл:

```sh
./scripts/build-skill.sh        # → dist/jyotish-reading.zip, ~50 КБ
```

Скрипт разыменовывает симлинки и проверяет пределы формата (50 МБ на архив,
25 МБ на файл, 500 файлов) до загрузки, а не после.

Локально агенту, который читает открытый стандарт, достаточно самого
репозитория: скилл уже лежит в `.agents/skills/jyotish-reading`. Можно и
скопировать каталог в `~/.agents/skills/`.

### Что доступно где

| | Claude Code | ChatGPT / Codex |
|---|---|---|
| Методика, гейты, три шкалы, правила честности | да | да |
| Команды `/jyotish:*` | да | нет — скилл ведёт этапы сам |
| CLI: сбор, расчёт пути души, чек-лист, сверка | да | только если есть оболочка и Python |

**Скилл рассчитан на оба режима.** Там, где CLI недоступен, он переходит в
ручной: этап 01 выполняется по `references/01_*.md`, данные присылает человек.
Гейты, три шкалы, правило независимости подтверждений и запрет на выдумывание
чисел действуют одинаково в обоих режимах — на этом держится вся методика, и
режим запуска её не ослабляет.

### В облачных сессиях

Плагин ставится и там — проверено: `claude plugin marketplace add
serg123e/jyotish-map` и `claude plugin install jyotish@jyotish-map` работают,
launcher поднимает venv как обычно.

Но контейнер облачной сессии эфемерный: установка живёт до конца сессии.
Чтобы плагин появлялся сам, положите в репозиторий, где ведёте разборы,
`.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "jyotish-map": {
      "source": { "source": "github", "repo": "serg123e/jyotish-map" }
    }
  },
  "enabledPlugins": ["jyotish@jyotish-map"]
}
```

Документация называет `enabledPlugins` в `.claude/settings.json` штатным путём
именно для облачных сессий, где интерактивный `/plugin` может быть недоступен.
Маркетплейс добавляется без отдельного запроса после того, как папка репозитория
получила доверие. Учтите оговорку из документации: плагин из внешнего источника
может не установиться сам — тогда Claude Code покажет команду
`claude plugin install`, которую надо выполнить один раз.

### Из терминала, без Claude Code

```sh
pip install -e plugins/jyotish     # или просто plugins/jyotish/bin/jyotish
```

Данные берутся с [vedic-horo](https://vedic-horo.com) через
[`vedic-parser`](https://github.com/serg123e/vedic-parser). Астрономических
расчётов здесь нет и не будет: положения планет, куспиды и даты даш приходят с
сайта как есть.

## Этап 01: сбор данных

```sh
jyotish new ivan                  # создаст clients/ivan/chart.yaml
$EDITOR clients/ivan/chart.yaml   # дата, время, координаты, статус времени рождения
jyotish collect clients/ivan      # ~97 запросов к сайту, с кэшем
jyotish status clients/ivan       # что собрано, что осталось
```

Координаты — **градусы и минуты**, не десятичные: `55.45` значит 55°45′,
ровно как отправляет форма сайта. Отрицательные для юга и запада.

На выходе три файла:

| Файл | Что это |
|---|---|
| `01_RAW_DATA.md` | полный технический экспорт по всем разделам Промпта 01, с 1-го по 20-й |
| `01_MISSING_DATA.md` | чего нет и почему, маркерами из Промпта 01 |
| `state/summaries/01.md` | сводка для этапа 02 — вместо ручного копипаста |

### Про запросы к сайту

Каждый запрос заставляет сайт считать карту, поэтому ответы кэшируются в
`clients/<slug>/raw/` и между вызовами выдерживается пауза (`collect.throttle`,
по умолчанию 2 с). На сплошном проходе сайт всё равно может ответить `429` — тогда
сбор останавливается с внятным сообщением, а уже полученное остаётся в кэше:
повторный запуск продолжит с того же места. `--refresh` пересобирает всё заново.

Кэш привязан к параметрам карты. Если время рождения ректифицировали, старые
ответы не подмешаются: сборщик откажется работать и попросит `--refresh`.

## Этап 07: пройденность пути души

Промпт 07 запрещает назначать итоговое число «по общему впечатлению». Поэтому
модель выставляет только шесть баллов слоёв — **с обоснованием каждого**, — а
взвешенную сумму, подшкалы и таблицу вкладов считает код.

```sh
jyotish soul-path clients/ivan --template   # заготовка soul_path_input.json
jyotish soul-path clients/ivan              # посчитать, записать главу
```

Этап отказывается работать, а не выдаёт число послабее, когда:

* время рождения не подтверждено и не ректифицировано — гейт самого Промпта 07;
* нет данных D60, на который приходится 30% веса;
* у слоя выставлен балл без обоснования — это и есть «общее впечатление» с цифрой.

Отсутствие D20 — единственное послабление, которое промпт разрешает: его 10%
делятся между D1 и D9, и это печатается в главе, а не остаётся догадкой.

## Этап 10: чек-лист качества

```sh
jyotish check clients/ivan       # пишет qa.md, ненулевой код возврата при провалах
```

Из 27 пунктов Промпта 10 код решает 13: три шкалы не перепутаны, таблица слоёв
на месте, оговорка про 0% есть, гейт 07 соблюдён, камни идут после таблицы
функциональных ролей, приоритет медицины назван, доля терминологии в пределах
20%, у каждого паттерна ≥3 подтверждения из разных слоёв.

Остальные 14 требуют смысла и помечаются **«нужен читатель»** — не «пройдено».
Чек-лист, который тихо пропускает половину пунктов, хуже, чем его отсутствие.

## Сверка со вторым источником

vedic-horo — один источник. Разбор на одном источнике настолько же верен,
насколько верен источник, и конвейер этого не заметит.

```sh
pip install -e 'plugins/jyotish[crosscheck]'
jyotish crosscheck clients/ivan       # пишет crosscheck.md
```

Второй расчёт делает [jyotishganit](https://github.com/northtara/jyotishganit)
(MIT, эфемериды NASA JPL через skyfield). Сверка **не выбирает победителя**:
совпадение поднимает доверие к числу, расхождение означает, что одному из
источников верить нельзя, и это надо выяснить, а не усреднить.

Что сверяется:

| | vedic-horo | локально |
|---|---|---|
| Сидерические долготы семи планет | — | совпали до 0.02′ |
| Накшатры и пады | — | совпали все |
| САВ по 12 домам | — | совпал полностью |
| Заявленная айанамша против фактической | — | сходится до 0.01′ |
| Раху и Кету | Близнецы 0.39° | Телец 28.44° — средний против истинного узла |
| Бхава-бала | не считает | есть |

Расхождение узлов — не дефект: средний и истинный узел это разные точки.
Сверка называет это, а не усредняет.

### Первое «расхождение» оказалось ошибкой самой сверки

Стоит того, чтобы остаться в README. Сначала сверка объявила, что vedic-horo
заявляет айанамшу, с которой не воспроизводятся его же положения: 14′ на
тестовой карте, 16.7′ на второй. Вывод был неверен, **сайт прав**.

Айанамша — это угол от точки весеннего равноденствия **на дату карты**. У
skyfield `ecliptic_latlon()` без аргумента отвечает в эклиптике J2000, и разница
между этими двумя системами отсчёта есть в точности прецессия, накопленная между
картой и 2000 годом: 0.2765° для 1980 года — те самые 16.6′. Величина «находки»
менялась от карты к карте пропорционально её году, что и выдало причину.

После `epoch=` заявленная айанамша сходится с фактической до 0.006′. Урок не в
том, что сверка бесполезна, а в обратную сторону: **второй источник умеет
производить расхождения на пустом месте**, и проверять надо в том числе сам
проверяющий. Регрессия закрыта тестом на подставных эфемеридах — он падает,
если `epoch` снова потеряется.

## Что считает код, а не модель

Прямо в `plugins/jyotish/jyotish/derive.py`, потому что у этих величин один правильный ответ:

* **арудха-пады** A1–A12, AL, UL, Дара-пада — сайт их не отдаёт;
* **диспозиторы** и паривартана;
* **чара-караки** по наибольшему градусу — и сверка с тем, что показывает сайт.
  Неверная Атмакарака названа в методике как повторяющаяся ошибка, поэтому она
  считается независимо, а расхождение печатается блоком `РАСХОЖДЕНИЕ`, а не
  разрешается молча;
* **сила домов** — три показателя на дом: бинду САВ, шадбала управителя и
  дришти на дом.

Всё вычисленное здесь помечено в экспорте как **[расчёт]** — читатель должен
отличать нашу арифметику от данных сайта.


## Границы

Варшапхала и транзиты закрыты платным доступом. Всё это попадает в
`01_MISSING_DATA.md` с причиной, а не заполняется догадкой.

**Бхава-балы нет и она не реконструируется.** Бхавадхипати-бала доступна
напрямую, но Бхава-Диг-бала требует классической таблицы, а формулу
Бхава-Дришти-балы воспроизвести не удалось: собственная дрик-бала планет у
сайта не выводится из его же матрицы аспектов. Собранное наполовину по памяти
число выглядело бы точным и не было бы проверяемым. Поэтому — три показателя,
каждый прослеживается до цифры сайта, и они намеренно не складываются.
